## Introduction

This document is meant to serve as a guide to maintaining and modifying the CUCCA VM Network Mailer.  In addition to program logic descriptions, guidelines are provided for writing <em>Mailer</em> user exits.  The version of <em>Mailer</em> described is experimental version 1.0 (x1.0).

## Environment

<em>Mailer</em> was developed under CMS/BSEPP version 6 PLC 17.  It has run under VM/SP with no need to be reassembled.  The following areas may cause trouble if an incompatible release of VM/CMS comes out:

- <strong>DMSSCANN</strong> — The CMS tokenizer.  The NUCON symbol ASCANN is used to obtain access to this routine and the DMSKEY macro is used to get into system key.
- <strong>LOCCNT</strong> — Used by the CMS loader.  This NUCON value is used in conjunction with an SVC 202 CMS LOAD command using the ORIGIN option.
- <strong>SFBLOK</strong> — CP Spool file blocks are referenced using the SFBLOK dsect described in member SPOOL of DMKMAC MACLIB.
- <strong>VMCMHDR</strong> — VMCF dsects from DMKMAC MACLIB are used for SMSG support.
- <strong>RSCS tag</strong> — The text of the tag generated by RSCS/Networking is assumed to have a fixed offset at which point the origin node name and userid are described.  This offset is described in the RSCSTAG dsect in MAILER MACLIB.

<em>Mailer</em> is designed to operate as a CMS disconnected virtual machine. It normally does not require any attention by operations personnel. The VM userid for <em>Mailer</em> should be configured in the following manner:

- <strong>VM Size</strong> — A minimum of 512K is suggested.
- <strong>VM Userid</strong> — Something self-descriptive such as "Mailer" or "VMMail" is recommended although not required.  Remote users will receive messages from this userid when they send mail to users on your system.   The userid,  once established,  should not be changed without first informing the person supporting <em>Mailer</em> for your network since all <em>Mailers</em> in  the network maintain a table of the names of other <em>Mailers</em>.
- <strong>191 Minidisk</strong> — A writeable CMS minidisk is required for <em>Mailer</em> use. Additionally the same or another minidisk is required to store the <em>Mailer</em> modules and parameter file.  It is recommend that this be a seperate read-only disk that your site's maintainer has write  access to.  This eases maintenance but is not required.
- <strong>Priviledge Classes</strong> — Class G priviledges are all that are required,  although the addition of class D priviledges will allow for the use of MSGNOH,  leading to more readable messages from <em>Mailer</em>.

## Generation

<em>Mailer</em> is written in 370 Assembler.  <em>Mailer</em> may be reassembled by using the MAILGEN CMS exec. The needed Global Maclibs  (for BSEPP) are:  MAILER, CMSBSE,  CMSLIB,  OSMACRO,  DMKMAC.  Make sure the DMKMAC MACLIB is last in the search order since it contains a CALL macro that is incompatible with the OS CALL macro found in OSMACRO.

Once assembled, <em>Mailer</em> may be loaded and gen'd via:

```text
LOAD MAILER

GENMOD MAILER
```

## Operation

To run <em>Mailer</em>,  the MAILER TXTLIB  must be global'd or the TEXT files for the user exits must be available.  Simply type "Mailer" and it will start.  It is suggested that this procedure be put in a CMS PROFILE EXEC.  Then <em>Mailer</em> may be started by issuing the CP AUTOLOG command from the operator console or a service disconnected machine such as VMUTIL.

<em>Mailer</em> reads an initialization file whose default name is MAILER PROFILE.  If this file is found and processed properly,  then <em>Mailer</em> will become operational.  If not,  then error messages are printed and <em>Mailer</em> will exit.

## Data structures - MAILBLOK

<em>Mailer</em> communicates with all it's routines almost exclusively through the MAILBLOK data area.  This central data area is gernerated and referenced via the MAILBLOK macro in MAILER MACLIB.  The following sections describe some of the key fields of the MAILBLOK.

### Stack pointers

Most routines allocate storage from a common stack.  A stack pointer is a doubleword containing the next free address in the first word and the remaining length in the second word.  Other buffers also sometimes use this method of description.  The stack pointers are:

- <strong>STACKORG</strong> — Stack origin.  This is the beginning address of the stack allocated via GETMAIN in MAILER.
- <strong>STACK</strong> — Variable stack start.  The area between STACKORG and STACK contains static information that is set once during initialization.  This consists of tables from the Mailer Profile and the dynamically loaded user exit routines.
- <strong>STACKP</strong> — Current variable stack pointer.  As each mail file is processed, stack storage is allocated using STACKP. STACKP generally tends to grow (i.e. more stack space is used) without ever shrinking.  The order of processing usually precludes freeing any stack space until all work is completed.  At this point, STACKP is reset to the value in STACK (in MAILER).

### MAILHBUF, MAILHREC, MAILHLIN

MAILHBUF  is a pointer to the buffer (allocated from the stack) which contains the text of the message header as read in from the mail file.  Trailing blanks are trimmed and X'15' (newline) characters used to delimit records.

MAILHREC  contains the number of physical records in the header (i.e. how many cards read in). MAILHLIN contains the count of logical records in the header. This number is usually the same but may be greater if X'15' characters were imbedded in a physical record.

### MAILPTAB

  This is the parameter table.  Entries of the form &lt;keyword&gt;=&lt;value&gt; may be specified in the Mailer Profile file.  An entry is created in the MAILPTAB TBLUK table (TBLUK described below) with the keyword as  the key and the value character string as the value.  Later calls to TBLUK can be used to find both keywords recognized as <em>Mailer</em> keywords and user-defined keywords for use by the user exits.

### MAILRTAB

  This is the Outgoing table.  The key used is the alias or host name and the value for each entry is a pointer to a ROUTD dsect (described below).

### MAILSTAB

  The special handling table is used for userids that receive special treatment (i.e. SYSTEM, etc.)  The key for each entry is the userid and the value is a pointer to a ROUTD.

### MAILVTAB

  The incoming table is used for validity checking of mail from other network mailers.  The key consists of the concatenation of the  RSCS node name (padded to 8 characters) and the VM userid of the mailer userid at the remote site.  Note that this organization  allows one site to have multiple mailers (useful since an RSCS RJE station looks like a userid).  The value for each entry is a pointer to a VALD dsect described below.

### MAILKTAB

  The keyword table is built as each mail file is parsed.  The key to each entry is the field name (i.e. "from", "to", "cc", etc.) and the value is a pointer to a field descriptor (FIELDD) dsect.

### MAILFLD, MAILSFLD, MAILCMDL

    Pointers to various lists are maintained in MAILBLOK.  MAILFLD  points to the list of FIELDD's that describe the message header. MAILSFLD points to the FIELDD which describes the sender of the mail file.  MAILCMDL points to a list of commands to be  executed by MAILCMD2.  The list is built by MAILCMD1.

### MAILSFB, MAILFILE, MAILFTXT

    The SFBLOK for the current reader file is in MAILSFB.  MAILFILE is another copy of the file number and MAILFTXT is the character version of the file number.

### MAILOPTS - options flags

  The MAILOPTS flags are set from values in the Mailer Profile as well as by commands.  Flags and their meanings are:

- <strong>MOPTDEF</strong> — Default values for omitted "date:" and "from:" fields from local users should be supplied (NYI).
- <strong>MOPTAUN</strong> — Mail from and to unknown hosts (not in MAILVTAB, or MAILRTAB) is allowed if this flag is on. This is useful in a network envirnonment where the RSCS tables have been updated prior to updates to the Mailer Profile.

### MAILCMD - command flags

  The flags in MAILCMD describe commands for Mailer to execute.  These are:

- <strong>MCMDRELD</strong> — Reload the Mailer.
- <strong>MCMDHALT</strong> — Terminate processing.
- <strong>MCMDCMD2</strong> — Some commands are queued on the chain pointed to by MAILCMDL.  Call MAILCMD2 to process them.

### MAILSTAT - status flags

  The MAILSTAT flags reflect the current execution status of <em>Mailer</em>. These are:

- <strong>MSTINWT</strong> — <em>Mailer</em> is currently is wait state for a console or reader interrupt.
- <strong>MSTQSC</strong> — <em>Mailer</em> is currently quiescant. This means that reader interrupts are accepted but no processing of files is performed.  All other functions are still active.

### MAILFLG1 - file flags

  The MAILFLG1 flags describe the status of a particular mail file.  These are:

- <strong>MFLG1LCL</strong> — File is from a local user.
- <strong>MFLG1GTW</strong> — File is from a gateway interface.
- <strong>MFLG1EDI</strong> — Message header has been edited to appear differently from original.
- <strong>MFLG1REJ</strong> — File has been returned by RSCS (rejected).
- <strong>MFLG1HDS</strong> — The message header has been successfully scanned.

### Other variables

- <strong>CPUSTR</strong> — RSCS node name of this system.
- <strong>RSCSNAME</strong> — VM userid of RSCS/Networking server.
- <strong>MAILVMID</strong> — VM userid of the Mailer. Obtained at initialization via CP diagnose.
- <strong>MAINTID</strong> — VM userid of the maintainer.
- <strong>MAINTNOD</strong> — RSCS node name for the maintainer.
- <strong>MAILNODE</strong> — Mail file origin node name extracted from the RSCS tag if not local.
- <strong>MAILUSER</strong> — Mail file origin userid.
- <strong>MAILRTFN</strong> — Mailer Profile file name.
- <strong>MAILULFN</strong> — Temporary error log file name.

## Data structures - Other Control Blocks

Several DSECTS are described in the BLOCKS macro of MAILER MACLIB.  A brief description of the fields of each follows:

### TOKEND - Token Descriptor

Character strings read by <em>Mailer</em> are tokenized prior to parsing.  These tokens are described by the TOKEND dsect.  Fields in a TOKEND are:

- <strong>TOKSTR</strong> — Address of character string described by the token.
- <strong>TOKLEN</strong> — Length of the string.
- <strong>TOKNEXT</strong> — Address of next TOKEND in order of appearance.
- <strong>TOKCODE</strong> — Code for type of token.  Types are: ATOM, QUOTED STRING, LEFT BRACKET,  RIGHT BRACKET, ATSIGN, COMMA, COMMENT.

The use of TOKENDs makes editing the message header (when necessary) easy to do.  A new TOKEND can be created with it's string located in storage seperate from the current string of tokens.  It can then be inserted into the token list by simply modifying two TOKNEXT pointers.  This is normally not done,  but might become necessary when processing host lists or when a file has to be edited to conform to another mail system.

### ADADDR and ADNODE - Address descriptors

The ADADDR and ADNODE dsects are used in the representation of addresses and address lists.  An address is described by a tree structure with the ADADDR at the root.  Address lists consist of linked lists of the ADADDR trees.  See figure [ADPFIG](#adpfig) for an example.  Fields in the ADADDR are:

- <strong>ADANEXT</strong> — Address of next ADADDR record.
- <strong>ADAUCNT</strong> — Number of ADNODEs used in the description of the user name.
- <strong>ADAULST</strong> — Address of first ADNODE in the user name list.
- <strong>ADAHCNT</strong> — Number of ADNODEs used in the description of the host path.
- <strong>ADAHLST</strong> — Address of first ADNODE in the host path list.

### FIELDD - Field descriptor

FIELDD blocks are used to describe a message header field.

- <strong>FINEXT</strong> — Address of next FIELDD in order of apperance.
- <strong>FIEXTN</strong> — Address of next FIELDD that is an extension (i.e. has the same field name).
- <strong>FIFLG</strong> — Flags:

  - <strong>FINVFLG</strong> — (Set by the field parser) Indicates that the field is "invisible".  That is, it should not be output when the mail file is sent.  This is used to hide password fields and other inter-mailer communication information that the user shouldn't see.
  - <strong>FIEXTFLG</strong> — Indicates an extension FIELDD.
- <strong>FISTR</strong> — Beginning address of field string.  Points just after the colon that follows the field name.
- <strong>FIEND</strong> — End address of field string.
- <strong>FITOK</strong> — Pointer to token list.  The first token is the field name.
- <strong>FIPARS</strong> — Pointer to parse list.  Optionally used by some field parsers.

### ACTADR - Block for address requiring action

ACTADR blocks  are used to maintain a list of the Outgoing ROUTDs and ADADDRs that require action (i.e. this <em>Mailer</em> is a server for).  Fields are:

- <strong>ACTNEXT</strong> — Address of next ACTADR.
- <strong>ACTADA</strong> — Address of ADADDR record for the address requiring action.
- <strong>ACTRT</strong> — Address of ROUTD for the host named in the address.

## Modules

This section describes the function of each module in some detail. Further specifics may be found in the source to the named module.

### Standard subroutine linkage

OS standard linkage conventions are used.  In most cases,  the OS CALL macro is used.  Unless otherwise noted,  the modules described below are called with a single argument:  the MAILBLOK address.  The following return codes interpretations are used except for some special cases:

- <strong>0</strong> — No error.  This module has completed succesfully.
- <strong>4</strong> — Minor error.  For example, the user specified something wrong in his mail  file and it should be returned.
- <strong>8</strong> — ??? I don't remember.
- <strong>12</strong> — Internal error caught.  Probably due to a stack overflow or some other detectable but not immediately correctable error.
- <strong>16</strong> — Unknown error.

### MAILER - Main program

<u>Called By</u> CMS.

<u>Calls</u> READINIT, SETINIT, MAILSMSI, MAILMAIN, MAILCMD1, MAILSMSD, MAILCMD2, MONWTR, LCLMOD.

<u>Function</u>

1. Write startup message.
1. Variable GETMAIN for maximum available storage.
1. Calls LCLMOD routine if one was linked in.
1. Issue CP diagnose to get userid running under.
1. Call READINIT to read Mailer Profile.
1. Call SETINIT to set assorted MAILBLOK variables.
1. Call MAILSMSI to set up SMSG interrupt hanlder.
1. Check for any command flags and take the appropriate action: <a id="mainloop"></a>

   - <strong>MCMDRELD:</strong> — Reload by branching back to the top.
   - <strong>MCMDHALT:</strong> — Call MAILSMSD  to disable SMSGs and exit.
   - <strong>MCMDCMD2:</strong> — Call MAILCMD2 for more difficult command processing.
1. Call MAILMAIN to handle any reader files.
1. Wait for a Console or Reader interrupt.
1. For console interrupt,  call MAILCMD1 to parse the console issued command. Go to [MAINLOOP](#mainloop).
1. For reader interrupt,  go to [MAINLOOP](#mainloop).

### READINIT - Read Mailer Profile

  <u>Called by</u> MAILER.

<u>Calls</u> UNIXSCAN, TBADD, TBLUK, MONWTR.

<u>Mailer Profile format</u>

The Mailer Profile is a CMS file that has no restriction on RECFM or LRECL.  Data within the file is composed of keyword definitions and table definitions.  Blanks lines are ignored. Comments are indicated by a semicolon and may appear anywhere on a line.  Everything from the semicolon to the end of the line is ignored.  Alphabetic case is ignored and values in keyword assignments are converted to upper case.

Keywords are defined by a keyword followed by the symbol "=" followed by a single character string. Blanks are considered a delimiter. Tables are defined by the table name followed immediately by a colon. The table name must be one of "INCOMING", "OUTGOING", or "SPECIAL". A table end is marked by the keyword "END" followed by the table name.

<u>Function</u>

1. Find Mailer Profile via FSSTATE using MAILRTFN as the source of the file name.
1. Use the LRECL from FSSTATE to allocate a single record input buffer at the top of the stack.  Open the file.
1. (Pass 1) Call the PASS subroutine with the addresses of a keyword counting and table entry counting routine as parameters.  These routines count the number of entries in a given table and the number of keyword  assignments seen.
1. Allocate storage from the stack for the 4 tables (MAILxTAB) using the entry counts from Pass 1.
1. (Pass 2) Call the PASS subroutine with the addresses of a keyword entry and table entry creation routine as parameters.  These routines build the table entries and add them to the tables via TBADD.
1. Close the input file and free the input buffer from the stack top.

### SETINIT - Set initial values

  <u>Called by</u> MAILER.

<u>Calls</u> TBLUK, LOAD, MONWTR.

<u>Function</u> SETINIT scans the data read by READINIT and sets MAILBLOK variables from it.  It also causes the user exits named in the tables to be dynamically loaded.

1. The MAILPTAB (parms table) is scanned for <em>Mailer</em> keywords.  These keywords are:

   - <strong>ThisNode</strong> — RSCS node name of this system.
   - <strong>RSCSname</strong> — Userid of RSCS server.
   - <strong>MaintUser</strong> — Userid of maintainer.
   - <strong>MaintNode</strong> — Node name of maintainer.
   - <strong>Allow-Unknown-Nodes</strong> — Value for flag MOPTAUN in MAILOPTS. Is either "TRUE" or "FALSE".
   - <strong>Supply-Default-Fields</strong> — Value for flag MOPTDEF in MAILOPTS.

   The keywords fall into two categories: 8 character values to be filled in and bits to be turned on or off.  These are encoded in the tables PTABARR and PBITARR and may be easily expanded.
1. The MAILRTAB table is processed by the LOADRTAB subroutine.  Correct values are checked and the named user exits are dynamically loaded by the LOAD routine.
1. LOADRTAB is called for the MAILSTAB table.
1. Similarly,  the MAILVTAB entries are checked and the validation user exits are loaded.

### MAILMAIN - Main reader file processing routine

<u>Called by</u> MAILER.

<u>Calls</u> GETSPOOL,  GETHDR,  HDRSCAN,  VALIDATE,  BUILDLST,  SENDLST, MAILRET.

<u>Function</u>

1. Call GETSPOOL to get the spool file information. If the file is not valid for some reason,  go to step [RTS](#rts). If the reader is empty, return. <a id="chkrdr"></a>
1. Call GETHDR to read in the message header.  An erroneous header results in a transfer to [RTS](#rts).
1. Call HDRSCAN to parse the header fields.  An error results in step [RTS](#rts).
1. Call VALIDATE to check the semantics of the syntactically correct header.  Invalid semantics results in step [RTS](#rts).
1. Call BUILDLST to build a list of recipients.
1. Call SENDLST to actually send mail to the recipients on the list built.
1. Purge the reader file and go back to [CHKRDR](#chkrdr) to check for any more files.
1. (Return to Sender) <a id="rts"></a> Call MAILRET to return the erroneous file to it's sender if possible.

### GETSPOOL - Get spool file info

<u>Called by</u> MAILMAIN.

<u>Calls</u> MONWTR.

<u>Function</u>

1. Issue CP diagnose x'14' subcode x'FFF' to get the next SFBLOK. <a id="getsfb"></a> If the reader is empty, return with a return code to indicate that.
1. If the SFBLOK is marked in use, go to [GETSFB](#getsfb) to try for the next file.
1. Convert SFBFILID to character into MAILFTXT for later use.
1. Check SFBORIG to see it the file is from a local user or RSCS.
1. If local, set the MFLG1LCL and copy SFBORIG to MAILUSER and CPUSTR to MAILNODE.
1. If from RSCS,  turn off MFLG1LCL and obtain MAILUSER and MAILNODE from the tag text using the RSCSTAG dsect in MAILER MACLIB.  If the username is blank (from a locally attached RJE) set MAILUSER to  "SYSTEM".

### GETHDR - Read spool file header

  <u>Called by</u> MAILMAIN

<u>Calls</u> MONWTR

<u>Function</u>

Reads cards in via RDCARD macro and puts them in storage allocated on the stack.  Each card read has trailing blanks removed and a x'15' character added after it.  Cards are read until a blank card or EOF is encountered.  The address of the stack storage used for the header is put in the MAILHBUF pointer . The MAILHREC counter contains the number of cards read and the MAILHLIN counter contains the number of x'15' (newline) characters in the header buffer.  This allows imbedding multiple newlines in a single card.  The ":READ" card generated by the CMS PUNCH command is tested for and ignored if present.

### HDRSCAN - Scan message header

<u>Called by</u> MAILMAIN.

<u>Calls</u> TBADD, TBLUK, APARSE, DPARSE, DEFPARS, DESTPARS, MONWTR.

<u>Function</u>

HDRSCAN parses the message header pointed to by MAILHBUF. Each header field name (i.e. "from", "subject") has a parser associated with it in the PARSERS  table.  New field parsers are easily added into this table. A default parser,  DEFPARS,  is called for field names that don't appear in the table.

1. Allocate the field name TBLUK table,  MAILKTAB,  from the stack.
1. Scan the header buffer for a keyword.  This is defined as starting at the left margin and delimitted by a colon.<a id="nextfld"></a>
1. Once a keyword is found,  scan until the beginning of the next keyword is found to get the start and end addresses of the header field.
1. Fill in a FIELDD with FISTR set to point just after the colon and FIEND to point just prior to the next keyword (or buffer end).
1. Allocate a TOKEND for the field name and put its address if the FITOK field.
1. Chain the FIELDD after the previous FIELDD with the anchor of the list at MAILFLD.  This list can be used later to access the fields in order of appearance in the header.
1. Call TBADD to add the field name to MAILKTAB.  The field may already have been added before.
1. If the field was already there, then this is defined as an "extension field".  That is, another occurence of the same field name elsewhere in the header.  This is legal syntax and semantically can be considered as a concatenation of the data to the previous data for the field.  The FIEXTN pointer in the previous FIELDD for the field is set to point to the new FIELDD.  This allows later access to all FIELDDs for the same field name in the order of appearance.
1. If the field was not already there,  then it's keyword has been added to the table.  Subsequent routines may easily find the FIELDD for the required field by calling TBLUK with the field name required.
1. Go back to [NEXTFLD](#nextfld) until all field names have been processed.
1. Once all the field names have been picked up and FIELDDs built,  a second pass is taken through the MAILKTAB table.  Call TBLUK with the PARSERS table for the next MAILKTAB entry.<a id="nextfld2"></a>
1. If the entry is found,  the return value is the address of the parser to call.
1. If the entry is not found,  use the DEFPARS parser.
1. Call this parser with the FIELDD as argument. The parser is expected to add TOKENDs to the FITOK list and  may optionally use the FIPARS pointer for a data representation particular to the field type being parsed.
1. On an error return code from the parser,  return after issuing an error message and setting an error return code.
1. Continue until all fields have been parsed. Go to [NEXTFLD2](#nextfld2).

### APARSE, ADPARSE - Parse address fields

  <u>Called by</u> HDRSCAN

<u>Calls</u> TOKENIZR

<u>Function</u>

APARSE is called by HDRSCAN with a FIELDD as a parameter.  It  uses the FIELDD to build the parameter list for the actual address parser, ADPARSE.  ADPARSE takes as arguments the start and end address of the string to be parsed, a stack pointer, and pointers to be filled in for the token list and parse list. These output fields are filled in FITOK and FIPARS respectively by APARSE.

1. Call TOKENIZR to convert the input string into a linked list of TOKENDs allocated from the stack.  The entire input string is tokenized prior to parsing.
1. Chain through the token list.
1. Allocate an ADADDR  record and chain it from the previous one via the ADANEXT pointer.  The list anchor is  later returned and plugged into the FIPARS of the FIELDD.
1. For each user name token parsed,  allocate an ADNODE and set the ADNDOWN pointer to the TOKEND for the user name atom.  If a user name contains multiple atoms,  then a list of ADNODEs is produced, with each pointing to the next via the ADNNEXT pointer.  The number of ADNODEs in this list is put in the ADAUCNT field of the ADADDR record and the address of the first ADNODE in the list is put in the ADAULST pointer.
1. For each host name token parsed, allocate an ADNODE as in the previous step.  Each ADNODE here specifies the next host in a path (as in @HOSTA@HOSTB@HOSTC). The number of host name ADNODEs is put in the ADAHCNT field of the ADADDR and the ADAHLST field gets the address of the first ADNODE.

This module is currently being rewritten for the next release of <em>Mailer</em>.  It will output a very similar if not identical representation but will operate more elegantly than the current horrendous code and will support more of the RFC733 syntax.

### DEFPARS, DESTPARS, - Other field parsers

Other less complicated parsers are provided for non-address message header fields.  The functions of these parsers are:

- <strong>DEFPARS</strong> — The default parser creates one TOKEND for each line of text in the field.  Generally, this is only one but may be more if the header field contains multiple lines.  The token type is set to quoted-string.  FIPARS is not used.
- <strong>DESTPARS</strong> — This parser is for the "\*DESTINATION:" field used by the <em>Mailer</em> gateway function.  It creates one atom TOKEND for each hostname in a list seperate by commas or blanks.  FIPARS is not used.

### VALIDATE - Check validity of message

  <u>Called by</u> MAILMAIN.

<u>Calls</u> TBLUK, MONWTR.

<u>Function</u>

The required message fields are checked for as well as special funny cases such as a file that <em>Mailer</em> has sent to itself for the purposes of reporting an error or a file rejected by RSCS because of an invalid tag.

1. Check if the file was generated by <em>Mailer</em>. Test MFLG1LCL  to see if the file is locally generated and compare MAILUSER and MAILVMID for the same userid.
1. If the previous step is satisfied,  check the tag text for the special tag "--- returned mail file ---" which indicates it was generated by the MAILRET routine.  If so,  go on to step [NOTSPCL](#notspcl) for standard processing.  If not,  the file was probably rejected by RSCS.  Write an error message and set the MFLG1REJ flag to indicate this case.
1. Call TBLUK with the MAILKTAB table for the string "Date". <a id="notspcl"></a>
1. If "Date" is not found and MOPTDEF is off,  then the file is invalid.  Write an error message and return.  If MOPTDEF is on,  fill in a default "Date" field (NYI).
1. Call TBLUK to check for existence of "From" field.
1. If found,  test the FIELDD returned to see that the field has only one address and not a list.  If this is true, go on the [CHKSNDR](#chksndr).
1. Call TBLUK to check for existence of "Sender" field.  Test as in the previous step.  If this succeeds, go on to [CHKSNDR](#chksndr)
1. Test the MOPTDEF flag and supply the default sender if the file is from a local user only (MFLG1LCL on). (NYI)
1. Test the MFLG1REJ flag and return if it is set.<a id="chksndr"></a>
1. Test the MFLG1LCL flag and if off (file from network), go to step [NETWORK](#network).
1. (File from a Local sender) Look at the sender field and compare the sending userid to MAILUSER to see if the sender names match.
1. Look at the sender field host name by calling TBLUK with the MAILRTAB  table to see if the specified host name is an alias for the local system. (compare CPUSTR and RTROUTE of the ROUTD  returned.)
1. If the above tests succeed,  return successfully.
1. (File from a network sender) Call TBLUK with the MAILVTAB  table to see if there is a VALD for the named sender node (MAILNODE) and userid (MAILUSER)  .<a id="network"></a>
1. If one is found,  then check to see if a validation user exit (address in VAADDR) was supplied.  If so call it.  If not, return successfully.
1. If one is not found, check MOPTAUN to see if unknown nodes are allowed.  If off,  return failure.
1. If unknown nodes are allowed,  call TBLUK again to see if a default validation exit was supplied.  Call it if found, else return.

### BUILDLST - Build list of recipients

  <u>Called by</u> MAILMAIN

<u>Calls</u> TBLUK, MONWTR.

<u>Function</u>

BUILDLST generates a list of ACTADR blocks for each recipient  that <em>Mailer</em> is a server for.  This list is pointed to by MAILCHN in MAILBLOK.

1. Call TBLUK with MAILKTAB for each address field ("To", "CC", "BCC") and retain pointers to the FIELDDs for the fields that are found.
1. For each ADADDR list,  the BLDACT routine is called.
1. BLDACT: Get next ADADDR record.<a id="nxtada"></a>
1. Obtain the last host name TOKEND by following the list of tokens from ADAHLST to the end.
1. If MFLGDEST is on,  indicating "\*DESTINATION" gateway processing,  search the destination list to see if the host name is on it.  If not, ignore this ADADDR and  go to step [NXTADA](#nxtada).
1. Call TBLUK with the MAILRTAB table to find the entry for the named host.
1. If not found, see if the Allow-Unknown-Nodes option was specified (MOPTAUN on) and if so,  search MAILRTAB for a ROUTD for "\*DEFAULT\*". If found,  continue with the following steps, otherwise ignore this ADADDR and go to step [NXTADA](#nxtada).
1. If found, check if one of the following is true:

   1. MFLG1LCL is on -- File is from a local user.
   1. MFLG1GTW is on -- File is from a gateway server.
   1. MFLGDEST is on -- Usual logic is being overridden by the \*DESTINATION list.
   1. CPUSTR equal to RTROUTE field of ROUTD -- This <em>Mailer</em> is the server for files for the host.
1. If the above step is true,  then add the ADADDR and ROUTD onto the ACTADR chain.
1. If the step was false,  then ignore this address and go to step [NXTADA](#nxtada).

### SENDLST - Send mail using list of recipients

  <u>Called by</u> MAILMAIN.

<u>Calls</u> MONWTR,  outgoing user exits.

<u>Function</u>

1. Get the next ACTADR record from the chain pointed to by MAILCHN.<a id="snd1"></a>
1. Get the ROUTD from the ACTRT pointer in the ACTADR.
1. If the RTADDR is non-zero,  then call the user exit (whose name is in RTPROG and loaded address in RTADDR).
1. If the user exit return code is non-zero,  write a message and loop back to [SND1](#snd1) for the next ACTADR.
1. Once all ACTADRs have been processed,  return failure if any user exit had a non-zero return code.  Otherwise,  return success.

### MAILRET - Return to sender

  <u>Called by</u> MAILMAIN.

<u>Calls</u> MONWTR, ARPADATE, PUNHDR, PUNTXT, PUNCLS.

<u>Function</u>

1. (File from local user) If the file is from a local user (MFLG1LCL true) and was not rejected by RSCS (MFLG1REJ false)  then check to make sure the mail sender (MAILUSER) is not the same as the <em>Mailer</em> userid (MAILVMID).  If these are the same, an error loop has been detected.
1. If an error loop was detected,  then check to make sure that the maintainer,  MAINTID,  is not the same as the <em>Mailer</em> id.  If so,  just return after writing an error message.  If they are different, go to step [MRET](#mret) to return the file.
1. (File from network or rejected by RSCS) If the file was rejected by RSCS (MFLG1REJ true) or is from the network (MFLG1LCL false) then try to extract the userid that caused the error from the "from" or "sender" field.  If valid,  this field is pointed to by MAILSFLD.  This field is zero if the sender was not successfully parsed.
1. If MAILSFLD  is zero,  then try to send  the file to the maintainer with the appropriate loop checking done as described above.
1. Each entry of the ADADDR and ADNODE pointed to by MAILSFLD should be checked carefully even though it was already parsed.  <strong>This is the major source of bugs in <em>Mailer</em></strong> and will lead to infinite looping if care is not taken.
1. Given the sender field is correct,  go to step [MRET](#mret) to  return the file.
1. Spool the punch to self (i.e. "SP PUN TO \*") and set the punch tag to  "--- returned mail file ---" for communication with the VALIDATE routine.  <a id="mret"></a>
1. Punch a message header that explains an error has occured.
1. Punch the error log file (named in MAILULFN) if it exists.  This file contains the accumulated error messages.
1. If MFLG1HDS is true, indicating the header was properly scanned,  then call PUNHDR,  PUNTXT,  and PUNCLS to punch the message header,  punch the message text,  and close the punch.
1. If the header was not scanned,  just loop with RDCARDs and PUNCHCs to copy the reader file to the punch file.

A lot of bugs seem to pop up in this routine and in the punching exits it calls.  A lot of care must be taken to insure that assumptions that can normally be made about a file   are not made here since the file wouldn't be erroneous in most cases if those assumptions were true.

### MAILSMSI, MAILSMSG, MAILSMSD - SMSG routines

MAILSMSI initializes SMSG processing by doing a VMCF SENDX authorize and a HNDEXT SET with MAILSMSG as the external interrupt handler. It also turns on bit 0 of control register 0.

MAILSMSD disables SMSG processing by doing a VMCF unauthorize and a HNDEXT CLR.

MAILSMSG is entered on an external interrupt.  It tests the interrupt code for X'4001',  the VMCF function code for VMCPSENX,  and the VMCMUSER for "SYSTEM".  Any other interrupts are ignored as well as SMSGs with a zero data length.  It then calls MAILCMD1 to process the command received.

### MAILCMD1 - 1st level command processing

  <u>Called by</u> MAILER,  MAILSMSG.

<u>Calls</u> UNIXSCAN, TBLUK.

<u>Parameters</u>

- <strong>SENDER</strong> — Userid of sender (for smsgs) or \* (for others).
- <strong>STRING</strong> — Command string.
- <strong>CODE</strong> — 0 for command from console or 1 for command from SMSG.

<u>Function</u>

This reentrant routine may be entered either by a call from  MAILSMSG or from MAILER. In the former case, external interrupts are disabled.  MAILCMD1 only performs trivial commands such as <em>Mailer</em> internal commands and CP commands.  More complex commands are saved for MAILCMD2 .  Command functions:

- <strong>? or HELP</strong> — Send a short message describing commands.
- <strong>ACTIVATE</strong> — Turn off the MSTQSC  flag.
- <strong>CHECK</strong> — (NYI)
- <strong>CMS</strong> — Allocate a COMMAND  block in DMSFREE storage.  Copy in the command data and other information and add it onto the the command list pointed to by MAILCMDL .  If called from the console,  there is a possibility of being reentered via SMSG,  so disable external interrupts whenever MAILCMDL is modified.
- <strong>CP</strong> — Issue the CP command via Diagnose 8 and trap the reply in a buffer. Return this buffer to the command issuer.
- <strong>FORWARD</strong> — (NYI)
- <strong>QUIESCE</strong> — Set MSTQSC to true.
- <strong>RELOAD</strong> — Set MCMDRELD true.
- <strong>SHOW</strong> — Options are:

  - <strong>VERSION</strong> — Reply with the <em>Mailer</em> version number and last assembly date.
  - <strong>STATUS</strong> — Reply with some counters and interpretation of the MAILSTAT  status flags.
  - <strong>OUTGOING</strong> — Show the ROUTD contents for the named host.  "SHOW OUTGOING \*" will list all ROUTDs.
  - <strong>INCOMING</strong> — Show the VALD contents for the named node and userid pair. "SHOW INCOMING \*" will list all VALDs.
  - <strong>SPECIAL</strong> — Same as SHOW OUTGOING except use the MAILSTAB instead of MAILRTAB.
- <strong>SMSG</strong> — Set a flag indicating the reply should be SMSG instead of MSGNOH or MSG.  Go back and try the next token as the command name.
- <strong>STOP</strong> — Set MCMDHALT true.

Authorization is checked for all commands and falls into two classes: General and Privileged.  General commands may be issued via SMSG by any user.  Privileged commands are issued via SMSG from the maintainer or from the console.

### MAILCMD2 - 2nd level command processing

  <u>Called by</u> MAILER.

<u>Function</u>

1. Disable external interrupts.
1. Copy MAILCMDL pointer and clear it.
1. Enable external interrupts.
1. Get next COMMAND.
1. Check code for CMD202 (the only type currently recognized).
1. Issue ATTN LIFO via SVC 202 to stack the command and then issue SUBSET (RETURN to execute the command.
1. Release the DMSFREE storage and do the next COMMAND.

### PUNHDR, PUNTXT, PUNCLS - Output punching routines

  <u>Called by</u> User outgoing exits.

<u>Function</u>

These routines punch the output mail file in a standard way. It is not possible to simply copy the input file to the output file since some records in the input file should be discarded (such as :READ card, inter-mailer communication information) or the header may have been edited.

PUNHDR uses the FIELDD list anchored at MAILFLD to output the header.  If MFLG1EDI  is off, indicating that the header was not edited,  then each FIELDD is used to access the data in MAILHBUF.  Only the records pointed to by FISTR and FIEND for FIELDDs that have the FIINVFLG off are punched.  This allows an easy way to prevent output of certain input fields.

PUNTXT simply skips the first MAILHREC records in the input file and then copies the rest to the output file.

PUNCLS closes the punch and sets the filename to be the user name from MAILSFLD.  The filetype is set to "MAIL",  and the distribution code to the host name from MAILSFLD.

### MONWTR, USERLOG, WRITELOG, SNDRMSG - Message routines

  MONWTR is the centralized message writer routine.  All <em>Mailer</em> message skeletons are in the MSGTEXT CSECT.  Messages are of the standard error message form.  The first three letters of the message number is "MAI".  The second three indicate the module name. The letter after the three digit number indicates how the message is to be handled.  All messages are written to the console by calling WRITELOG.  They may also be written to the user error log file and sent as network messages.  The following letters have a special meaning:

- <strong>U</strong> — Write to the user log file (MAILULFN) by calling USERLOG.
- <strong>X</strong> — Send the message to the file sender (from MAILSFLD)  by calling SNDRMSG  which issues an RSCS MSG command.

MONWTR is called by the WTR or LOG macros.  These macros differ only in that LOG requires MAILBLOK addressability to get the MONWTR address. This is the one needed for user exits.  The macro format is described in figure [WTRFIG](#wtrfig).

**Figure:** LOG macro format

<a id="wtrfig"></a>

```text
LOG mmmnnn[,(type,var,type,var,...)]
```

Where <em>mmm</em> is the three letter module identifier, <em>nnn</em> the three digit  message number, <em>type</em> the data type, and <em>var</em> any A-type address  constant or a register number coded within parentheses.

<em>types</em> are:

- <strong>D or DA</strong> — Decimal value or address of fullword.
- <strong>X or XA</strong> — Hexadecimal value or address of hexadecimal bytes (length determined by message skeleton).
- <strong>B or BA</strong> — Bit string value or address of bit string (length determined by  message skeleton).
- <strong>C or CA</strong> — Character string value or address of character string (length determined by message skeleton).

### TBLUK, TBADD - General table management routines

TBLUK is based on a DEC TOPS-20 Monitor Call of the same name. TBLUK performs table lookups and TBADD, additions.

A TBLUK table is a standard format table of doublewords. The left word points to a string descriptor which contains flags and the keyword string.  The right word is available to the user.  This word is normally called the dispatch value.  In <em>Mailer</em>,  this word is used in various places to contain record addresses (i.e. ROUTD, VALD),  branch addresses (command names table in MAILCMD1) and subroutine addresses (PARSERS table in HDRSCAN).

A TBLUK table may easily be build by using the TBSTART, T, and TBEND macros.  A sample TBLUK table defined with these macros follows. Note that the keywords must be specified in lexicographic order.

```text
CMDTABLE TBSTART ,		START OF COMMAND TABLE
	 T 'ADD',0
	 T 'DIVIDE'
 	 T 'MULTIPLY'
	 T 'SUBTRACT'
	 TBEND ,
```

For T macro entries that do not supply a dispatch value,  a symbol constructed of "$" followed by the first 7 letters of the keyword. For example, the dispatch values for the table above are: 0, $DIVIDE, $MULTIPL, $SUBTRAC.

<u>TBLUK parameters</u>

TBLUK is called by coding CALL TBLUK,(table,string,length,work) where <em>table</em> is the table address, <em>string</em> is the test string address, <em>length</em> is the string length,  and <em>work</em> is the address of a work buffer that has a maximum length of the length of the longest possible test string and the longest possible table keyword with a maximum of 512.

<u>TBLUK return values</u>

- <strong>Reg 0</strong> — Address of matched table entry.
- <strong>Reg 1</strong> — Dispatch value.
- <strong>Reg 15</strong> — 0 for exact match.  4 for unambiguous substring.  8 for ambiguous substring.  12 for no match.

TBLUK entries are mapped by the TBENTRY macro.  TBLUK keyword strings are mapped by the TBS macro.  The TBTAB macro maps a TBLUK table header. TBLUK is reentrant.

TBADD adds a new entry to a TBLUK table.

### LOAD - dynamic loader

  <u>Called by</u> SETINIT.

<u>Function</u>

LOAD is similar in concept to the OS LOAD macro.  It has the added advantages of being able to decide where a text is loaded and to prevent abends on trivial errors.  It is called with a stack pointer and routine name.  A "LOAD name (ORIGIN address NOMAP" command is built and issued via SVC 202.  The LOCCNT field in NUCON is checked to see how much space the loaded routine required. This amount is used to update the stack pointer.  It is possible for LOAD to clobber storage that follows the stack if the routine being loaded is too large.  This is highly unlikely however.

## User exits

This section should act as a guide to coding <em>Mailer</em> user exits. User exits are provided at the following points:

- As the LCLMOD exit called prior to READINIT in MAILER.
- A validation exit called in VALIDATE.
- An outgoing punching exit called in SENDLST.

### Calling conventions

All <em>Mailer</em> routines use standard OS subroutine linkage:

- <strong>R1</strong> — Address of parameter list.
- <strong>R13</strong> — Caller's register save area.
- <strong>R14</strong> — Caller's return address.
- <strong>R15</strong> — Entry point address.

These exits are loaded dynamically and therefore may not reference VCONS without the fear of the wonderful CMS loader blowing <em>Mailer</em> out of the water.  If a multiple module exit is required,  do the same thing that RSCS does:  use the PRELOAD module supplied with your RSCS system as per the instructions in the RSCS documentation.

### LCLMOD - Local Modifications hook

<u>Called via</u>

```text
CALL LCLMOD,(MAILBLOK)
```

This routine may be supplied by an installation to modify fields in the MAILBLOK prior to calling READINIT. This is mostly useful in a case where the name of the Mailer Profile is not known until runtime (i.e. on a site with 2 cpu's sharing dasd). In this case, LCLMOD can check the processor serial number (via STIDP instruction or CP QUERY CPUID) and set the appropriate file name in MAILBLOK accordingly.

### VALD exit

<u>Called via</u>

```text
CALL exit,(MAILBLOK)
```

This exit is called after the file has been parsed.  It is free to check anything it wants to look at in MAILBLOK.  A non-zero return code tells <em>Mailer</em> to return the file to its sender.

This exit should zero the MAILSFLD pointer if it determines that the sender field is bogus and could cause problems when trying to return the mail.

By using a keyword such as "PASSWORD:" and the FIINVFLG flag in the FIELDD for it,  a simple method of password-protecting a file over a non-secure HASP link has been done in the DECVER exit at CUCCA.  The keyword may be found by calling TBLUK with the MAILKTAB table.  Use of FIINVFLG on the  FIELDD prevents the password from being copied to the output file.

An example of a simple password-checking VALD exit follows:

```text
VALCHK  CSECT ,
	STM   14,12,12(13)
	LR    12,15		ADDRESSABILITY ETC.
	USING VALCHK,15
	ST    13,VALSAVE+4
	LA    13,VALSAVE
	L     11,0(1)		GET MAILBLOK BASE
	USING MAILBLOK,11
	L     5,MAILKTAB	GET KEYWORD TABLE
	L     15,ATBLUK		ADDRESS OF TBLUK
	CALL  (15),((5),KEY,L'KEY,WORK)
	LTR   15,15		FIND IT?
	BNZ   NOKEY		SORRY...
	LR    6,1		GET BETTER HANDLE ON THE FIELDD
	USING FIELDD,6		ADDRESS IT
	OI    FIFLG,FIINVFLG	MAKE THIS FIELD "INVISIBLE"
	L     1,FITOK 		POINT TO THE "PASSWORD:" TOKEN
	ICM   1,B'0111',TOKNEXT GET NEXT TOKEN
	BZ    NOKEY		"PASSWORD:" BUT NOT PASSWORD!
	USING TOKEND,1		ADDRESS THE TOKEN
	CLI   TOKLEN,L'PASS 	SAME LENGTH AS PASSWORD?
	BNE   NOKEY		SORRY...
	ICM   1,B'0111',TOKSTR  POINT TO STRING
	DROP  1
	CLC   PASS,0(1) 	COMPARE PASSWORDS
	BNE   NOKEY		SORRY....
	SR    15,15		YAY!
RET	EQU   *
	L     13,4(13)
	L     14,12(13)
	LM    0,12,20(13)
	BR    14
NOKEY	EQU   *
	LA    15,4
	B     RET
KEY	DC    C'PASSWORD'
PASS	DC    C'SECRET-PASSWORD'
WORK	DS    64F
SAVE    DS    18F
	BLOCKS ,		MACRO TO GET ALL DSECTS
	MAILBLOK ,		...EXCEPT MAILBLOK
	END   VALCHK
```

### ROUTD exit

<u>Called via</u>

```text
CALL exit,(MAILBLOK,ACTADR)
```

This exit is responsible for transmitting the mail file in the reader to it's recipient.  It has access to the ROUTD and ADADDR for the recipient as well as the routines PUNHDR, PUNTXT, and PUNCLS pointed to by APUNHDR, APUNTXT and APUNCLS  in MAILBLOK.  TBLUK is pointed to by ATBLUK.

The example above for the VALD exit shows all the basic information necessary to code an outgoing exit.
